Everything below was read live on `spark-dd06` during the session. Two stacked causes, one of
which the issue body had, one it did not.

## Cause 1 — `node-ip` pinned to the other SSID's address

```
$ grep node-ip /etc/rancher/k3s/config.yaml
node-ip: 192.168.1.144
$ ip -4 -br addr show wlP9p1s0
wlP9p1s0  UP  192.168.1.203/24
$ systemctl show k3s -p NRestarts
NRestarts=241            # 255 after the route add, 273 five minutes later
$ journalctl -u k3s | grep level=error | tail -1
Shutdown request received: failed to start networking: unable to initialize network policy
controller: error getting node subnet: failed to find interface with specified node ip
```

k3s starts, the kubelet reports `node IP "192.168.1.144" not found in the host's network
interfaces`, the network-policy controller can't find the subnet, and the server shuts itself down
("Deactivated successfully" — a clean exit, not a crash). systemd restarts it; repeat. While it
loops, `127.0.0.1:6443` alternates between listening and refused, so every pod that talks to the
API server (`mynifi-0` for its coordinator Lease, `ingress-nginx`, cainjector, metrics-server)
flaps with it. `tls-san` already listed both `.144` and `.203`, so the API certificate was never
the problem.

The `.144`/`.203` pair is the two saved Wi-Fi profiles (`CLAUDE-CHECKIN.md` NvidiaSpark-1
§Network): `STARLINK` gives the box `.144`, `ATTyjuHfEi 1` gives it `.203`. k3s was last
configured on the STARLINK address; today the box is on the AT&T network.

**Fix (Steven ran both, sudo):**
```
sudo sed -i 's/^node-ip: 192.168.1.144$/node-ip: 192.168.1.203/' /etc/rancher/k3s/config.yaml
sudo systemctl restart k3s
```
Result: `healthz` → `ok`, `NRestarts=0`, node `Ready` with InternalIP `192.168.1.203`,
`kubernetes` endpoints `192.168.1.203:6443`. The embedded agent kept dialing the cached
`192.168.1.144:6443` supervisor address for ~90 s ("Remotedialer proxy error"), then pruned it
(`Stopped tunnel to 192.168.1.144:6443` at 14:58:10). `ingress-nginx` (hostNetwork) had been
probed at `http://192.168.1.144:10254/healthz` — 1073 restarts over 20 days — and came back
`1/1` on its own once its podIP refreshed to `.203`. `mynifi-0` stayed `7/7 Running` throughout
(2 restarts, both earlier); its Jetty answers and, through the ingress with the admin p12,
`/nifi-api/flow/current-user` → 200 and `/nifi/` → 200.

## Cause 2 — the VPN's default route swallows the service CIDR

The issue's diagnosis holds for the pod → ClusterIP path, it just wasn't what was keeping k3s
down. With `gpclient` (GlobalProtect over openconnect, `cloudera.gpcloudservice.com`) up:

```
default dev tun0 scope link                          # metric 0, no gateway
default via 192.168.1.254 dev wlP9p1s0 metric 600
10.42.0.0/24 dev cni0                                 # pods: fine
(no route for 10.43.0.0/16)
$ ip route get 10.43.0.1
10.43.0.1 dev tun0 src 10.19.12.60                    # ClusterIP into the tunnel
```

**Fix:** a `/16` for the service CIDR via the LAN gateway. It beats the `/0` default and
reproduces exactly what `ip route get 10.43.0.1` returns with the VPN down (`via 192.168.1.254
src 192.168.1.203`); kube-proxy DNATs the ClusterIP before the packet needs the gateway, so the
route only changes source-IP selection and keeps the traffic off `tun0`. Harmless with the VPN
down. Steven added it by hand first (`sudo ip route add 10.43.0.0/16 via 192.168.1.254 dev
wlP9p1s0`); afterwards, from inside `mynifi-0` with the VPN still up:

```
curl -sk https://10.43.0.1:443/healthz   →  HTTP 401   (API server answering; was exit 7 / 000)
```

The pod CIDR needs nothing: `10.42.0.0/24 dev cni0` is already there and this is a one-node
cluster (no remote flannel subnets).

**Persistence** — `files/issue-352/`:
- `k3s-vpn-route.sh` — idempotent: derives the non-tunnel default (`via <gw> dev <iface>`),
  `ip route replace 10.43.0.0/16 via <gw> dev <iface>` only when it differs, no-op otherwise, does
  nothing when there is no LAN default. Dry-run as the user with the route already correct → silent
  `rc=0`, derived `GW=192.168.1.254 IFACE=wlP9p1s0`.
- `k3s-vpn-route.service` (oneshot) + `k3s-vpn-route.timer` (20 s after boot, then every 30 s) —
  survives a VPN reconnect (openconnect's vpnc-script only adds and removes its own routes) and a
  Wi-Fi flap (the kernel drops the route with the link; the next tick puts it back).
- `install.sh` — `sudo bash files/issue-352/install.sh`: installs the three files, enables the
  timer, asserts the route once, prints the timer and `ip route get 10.43.0.1`.

A timer was chosen over a NetworkManager dispatcher or udev hook because it is the one mechanism
that can be verified on the box without bouncing the VPN, and it does not depend on whether NM
emits events for an openconnect-created `tun0` (it does not manage it).

## Chrome — the NiFi UI

Chrome 153 on Linux reads `~/.pki/nssdb` **if it exists**, otherwise `~/.local/share/pki/nssdb`
(the M146+ default; the trap is spelled out in `files/issue-226/nifi-admin-p12.sh`). The NiFi
identity lived in the default db:

```
~/.local/share/pki/nssdb   cfm-operator-ca (C,,)   nifi-admin (spark-dd06) (u,u,u) + key
~/.pki/nssdb               created 2026-09-16 02:18 (#347)   Cloudera AWC Internal CA only, no keys
/proc/<chrome>/fd          → ~/.pki/nssdb/cert9.db, key4.db    (Chrome started 13:22)
```

So the running Chrome had no client certificate to offer and Jetty reset the handshake. Fix
(user-level, nothing removed): import into the db Chrome has open.

```
certutil -d sql:$HOME/.pki/nssdb -A -t "C,," -n cfm-operator-ca -i ~/nifi-admin-spark/ca.crt
pk12util -d sql:$HOME/.pki/nssdb -i ~/nifi-admin-spark/nifi-admin.p12 -W nifi-admin
```
Then fully quit and relaunch Chrome (it loads the db at start).

## Still open

- **`node-ip` follows the SSID by hand.** The pin in `config.yaml` is the right thing with the VPN
  up (auto-detection would pick `tun0`'s address, the default-route interface), so a switch to the
  other Wi-Fi profile means: re-pin, restart k3s. Recorded as a register quirk with its check in
  `CLAUDE-CHECKIN.md`. The static reservation for `.203` (runbook "Still owed") removes DHCP drift
  on the AT&T network; it does not cover the SSID switch.
- **Two NSS databases.** Chrome will keep using `~/.pki/nssdb` while it exists. Both now hold what
  they need; merging them is a separate, deliberate step.
- Neither the route keeper nor the re-pin has yet been exercised through a VPN *reconnect* in
  this session — the timer's next tick after one is the check (`journalctl -u k3s-vpn-route`).
