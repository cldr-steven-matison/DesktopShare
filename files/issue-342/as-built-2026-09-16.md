## Blocker — REST Catalog not reachable from the box under the corp VPN

> **SUPERSEDED later the same day (2026-09-16) — see "Update — REST catalog read PROVEN" at the end of this file.** The blocker diagnosis below was partly wrong: the SG's `179.64.39.45/32` is a *stale VPN-pool exit IP*, not the home IP, and the box needs the VPN *up* to reach the semi-private environment at all. Adding the box's current VPN egress `/32` to the Knox SG unblocked the read; the SG entry was added for the window and revoked after.

The box egresses on **`165.1.200.190`** right now, because the corp VPN full tunnel is up
(`tun0` at `10.19.12.51`, from #347 Cloudera Anywhere / goes01 work — full tunnel routes all
public egress through Cloudera's corp network). The only external `/32` in the Knox SG on 443
is **`179.64.39.45`** — the home IP the issue expected the box to share with WindowsDesktop.

Direct proof from the box:
```
$ curl -sk -o /dev/null -w '%{http_code} %{time_total}s' --connect-timeout 8 \
    https://srm-iceberg-aw-dl-gateway.srm-iceb.a465-9q4k.cloudera.site/
http_code=000 total=8.00s        # exit 28 — TCP 443 never connects (SG drop)
```
DNS resolves the gateway to `18.217.156.27`; the connection is dropped at the SG, not a name
or route problem. So the §3.3 read paths (InvokeHTTP + Knox OAuth2, `GetIceberg`,
`QueryIceberg`) **cannot be validated from spark-dd06 while the corp VPN is up.**

This is a genuine posture conflict on one box, not a config typo:
- **VPN up** (needed for #347 AWC/goes01): egress `165.1.200.190`, not in the Knox SG → REST catalog blocked.
- **VPN down**: egress reverts to the home IP; if that is `179.64.39.45` (the WindowsDesktop IP already in the SG) the catalog works, but the box loses goes01 reachability.

Neither VPN change nor an SG edit was made — both are live-infra changes, and whitelisting the
shared, transient corp-VPN `/32` is the wrong fix. Resolution is Steven's call (drop the VPN
for a Public Cloud validation window, or add a stable box egress `/32` to the Knox SG).

## Update — REST catalog read PROVEN (2026-09-16, later same day, #342)

With the corp VPN **up** (egress `165.1.200.192`, route to the gateway via `tun0`), the only thing
between the box and the catalog was the Knox SG. `srm-iceberg-knox-sg` (`sg-0938cb277fe790c79`)
allowed only `179.64.39.45/32` on 443 — a **stale VPN-pool exit IP**, not a home IP. Adding the
current egress and re-probing unblocked it:

```
# add (temporary), validate, revoke
aws ec2 authorize-security-group-ingress --group-id sg-0938cb277fe790c79 \
  --ip-permissions 'IpProtocol=tcp,FromPort=443,ToPort=443,IpRanges=[{CidrIp=165.1.200.192/32,Description="DGX Spark #342 validation"}]'
bash ~/Documents/GitHub/iceberg-rest-catalog-demo/test-rest-catalog.sh poc_uc2 flights
bash ~/Documents/GitHub/iceberg-rest-catalog-demo/test-rest-catalog.sh poc_uc2 airlines
aws ec2 revoke-security-group-ingress --group-id sg-0938cb277fe790c79 --security-group-rule-ids sgr-036429a4064a2dd61
```

Result (full capture: `files/issue-342/rest-catalog-validation-2026-09-16T1344Z.txt`):
- Knox `client_credentials` → JWT (len 1081).
- `GET /v1/namespaces` → `default, information_schema, poc_uc2, sys`.
- `GET /v1/namespaces/poc_uc2/tables` → `airlines, flights`.
- `loadTable` on **both** tables → `metadata-location` (`s3a://srm-iceberg-buk-210e3813/…`; the weekly
  rebuild rotated the bucket from the `…-081550c7` recorded above) **plus IDBroker-vended S3 STS
  creds** (`s3.session-token`, `client.region=us-east-2`) under `X-Iceberg-Access-Delegation: vended-credentials`.

This proves §3.3 path 1 (the `InvokeHTTP`+Knox-OAuth2 interaction) at the HTTP level. The SG `/32`
was revoked afterward; the corp VPN exit rotates within `165.1.200.x`, so a `/32` goes stale — the
durable fix is the corp range.

### Not done — in-NiFi validation blocked by a VPN↔k3s routing conflict

Running the read *inside NiFi* (`InvokeHTTP`+OAuth2 CS, and native `GetIceberg`/`QueryIceberg`) was
attempted and could not be completed. The box's NiFi runs on k3s and reaches the API server at the
ClusterIP `10.43.0.1`; the corp full-tunnel VPN installs `default dev tun0` with **no route for the
ClusterIP range `10.43.0.0/16`** (`ip route get 10.43.0.1` → `dev tun0`), so the NiFi pod cannot
reach the API server, cannot complete cluster-coordinator leader election, serves Jetty 503, then
crash-loops (`nifi` container SIGKILLed ~3.5 min in by its liveness probe). A NiFi pod restart and a
`systemctl restart k3s` were both tried (Steven-authorized) and neither helped — kube-proxy can
rebuild its rules, but the VPN's default route diverts ClusterIP traffic regardless. **This box's
NiFi cannot function while the full-tunnel VPN is up**, and the VPN is required to reach AWS — a
mutually-exclusive posture on one box. Fix: a split-tunnel/route carve-out excluding
`10.42.0.0/16` + `10.43.0.0/16` from `tun0`. Tracked as its own infra issue [#352](https://github.com/cldr-steven-matison/DesktopShare/issues/352). `GetIceberg`/`QueryIceberg`
additionally need the `nifi-iceberg-read-bundle` NAR built (source-only) and deployed into the pod.

**Corrected on #352 (later the same day):** the outage had a second, primary cause the paragraph above
missed. `/etc/rancher/k3s/config.yaml` pinned `node-ip: 192.168.1.144` and the box's wifi DHCP lease had
moved to `192.168.1.203`, so k3s exited on every start (`failed to find interface with specified node ip`,
`NRestarts` 241→273) — the API server flapped, and every pod that talks to it flapped with it. The VPN
route carve-out was necessary for pod→ClusterIP traffic but did not by itself recover k3s; re-pinning
`node-ip` did. As-built, fix and persistence: `files/issue-352/as-built-2026-09-16.md`.
