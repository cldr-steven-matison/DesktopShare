Every boot from 1 to 10 ran kernel `6.17.0-1032-nvidia` — the same kernel as the 1.7-day boot. The kernel does not separate the good boot from the bad ones. It is, however, the only candidate trigger for the whole episode: the unattended apt run of 09-10 15:58 UTC (`-1031` → `-1032`, `linux-modules-nvidia-580-open`, a `linux-firmware` bundle, plus `nvidia-spark-limits` = a memlock limit and `nvidia-spark-ota-check` = scripts, neither relevant) sits between two weeks of clean running and the first boot that ever froze, and the journal back to 2025-07 has no earlier NVMe timeout of any kind. The signed-kernel changelog is a stub, so whether 1032 changed PCIe/NVMe power behaviour is not knowable from the box. Unproven; recorded as the likeliest trigger. The fix does not depend on it.

`vmstat` at the same moment: 41 → 58 processes blocked, 89 % iowait, `bi`/`bo` ≈ 0. D-state list: `jbd2/nvme0n1p2-8`, eight `kworker/u81:*+flush-259:0` (nvme0n1), `kblockd`, `systemd-journal`, `kubectl` in `bio_queue_enter`. The kernel answered ping throughout — only storage was dead, which is why the box "looked up" from the LAN and the console showed `systemd-journald: Failed to write entry`.

The drive: Samsung `MZALC4T0HBL1-00B07`, fw `NXHB202Q`, serial `S8C2NG0Y812469`, PCIe root port `0004:00:00.0` at 32 GT/s x4, 41 °C. APST was enabled (`nvme_core.default_ps_max_latency_us=100000`, ASPM policy `default`).

## 4. The fix

Boot 10 wrote `/etc/default/grub.d/nvme-apst-off.cfg` and ran `update-grub` (sudo journal 19:13:36):

```
GRUB_CMDLINE_LINUX_DEFAULT="$GRUB_CMDLINE_LINUX_DEFAULT nvme_core.default_ps_max_latency_us=0 pcie_aspm=off"
GRUB_TIMEOUT_STYLE=menu
GRUB_TIMEOUT=3
```

Committed copy: `files/issue-322/nvme-apst-off.cfg`; `install.sh` step 0 installs it and runs `update-grub` when it differs. Boot 11's `/proc/cmdline` carries both parameters; `/sys/module/nvme_core/parameters/default_ps_max_latency_us` = `0`.

## 5. Boot 11 on the flag

- Uptime at evaluation: **1 h 20 min** at 20:35 UTC, against 36–97 s for boots 4–10 on the same kernel with the same services disabled. `journalctl -k` for the boot: zero `nvme` timeout/reset/abort lines, zero hung-task reports.
- Service restore 21:04–21:09 UTC (uptime 1 h 55 min): k3s and `minifi-java` re-enabled, off-switch removed, `serve-boot.sh` recreated all six containers (vLLM healthy at T+4:35). `post-boot-verify.sh --no-post` at 21:09:37: **PASS 21/21**. The tier's model load is the heaviest disk read of the day; `journalctl -k` stayed clean through it.
- Gotcha hit on the way: `systemctl start nvidia-serve-boot` after `rm`-ing the off-switch is a no-op — the oneshot is already `active (exited)` from the exit-0 at boot. `restart` (or the script by hand) is the re-arm on the same boot. Header comment and CLAUDE-CHECKIN carry it now.
- SMART (`nvme smart-log /dev/nvme0`, read ~20:50 UTC on boot 11): `critical_warning 0` · `media_errors 0` · `num_err_log_entries 0` · `percentage_used 0%` · `temperature 36 °C` · `power_cycles 68` · `unsafe_shutdowns 25` (the hard resets of the day are in that count). The drive is healthy; the hang was the power state, not the media.
