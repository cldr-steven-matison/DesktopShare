The original ask on #226 had four research items: **(2)** NVIDIA's own documentation, **(3)** the DGX Spark community, **(4)** the three bookmarked X posts plus whatever else the accounts led to, and **(5)** GitHub integration examples. Building the box out on Cloudera's stack needed four more buckets nobody asked for by name but every later doc depends on — Kubernetes on GB10, Cloudera AI, Cloudera on AWS, and Cloudera Streaming Operator images on aarch64. **Versions.** [release-notes.html](https://docs.nvidia.com/dgx/dgx-spark/release-notes.html) puts the shipped baseline at DGX OS 7.5.0, driver 580.159.03, CUDA Toolkit 13.0.2, Canonical kernel 6.17, UEFI 1.110.13 [med]. Our own box came up on driver **580.173.02** and CUDA **13.0** with kernel 6.17.0-1031-nvidia (`CLAUDE-CHECKIN.md`) — newer driver, same kernel line, so any chapter quoting a driver number quotes ours, not the doc's.

Changelog highlights from the same page [med]: **Jul 2026** improved OOM handling for unified memory, toggleable 2 GB/4 GB display-reserved memory, cloud-init over DHCP/HTTP/TFTP, HDMI hot-plug fix. **Jun 2026** OTA updates made optional at setup, NVIDIA Sync Cluster Assistant for up to four devices, NCCL v2.30u1 with three-system ring topology. **Apr 2026** air-gapped deployment, USB/local repo installs, cloud-init site customization. **Jan 2026** ConnectX-7 hot-plug (18 W saved), Bluetooth audio, UEFI Wi-Fi/BT disable. **Nov 2025** Ubuntu 6.14 HWE kernel, JupyterLab on CUDA 13.0.2, unified-memory reporting fix. Separately, [dgx-os.html](https://docs.nvidia.com/dgx/dgx-spark/dgx-os.html) says DGX OS updates ship roughly twice a year (February and August) for the first two years, and [os-and-component-update.html](https://docs.nvidia.com/dgx/dgx-spark/os-and-component-update.html) adds 10-year OS support from Canonical via Ubuntu Pro [med].

**Known issues** ([known-issues.html](https://docs.nvidia.com/dgx/dgx-spark/known-issues.html), five items) [med]:

| Issue | Workaround |
|---|---|
| A non-supplied power adapter "may reduce performance, prevent boot, or cause unexpected shutdowns" | Use only the supplied adapter |
| `nvidia-smi` shows `Memory-Usage: Not Supported` on iGPU platforms | Expected — an integrated GPU has no dedicated framebuffer to report. Our box shows exactly this (`CLAUDE-CHECKIN.md`) |
| CUDA versions verified only against release-time hardware/software | Use NGC containers (PyTorch, vLLM, TensorRT-LLM) for current features |
| `cudaMemGetInfo` ignores memory recoverable from swap on UMA, so allocatable memory reads low | Read `/proc/meminfo` instead; flush cache with `sudo sh -c 'sync; echo 3 > /proc/sys/vm/drop_caches'` |
| An HDMI display can enter deep sleep and fail to wake | Press a physical button on the monitor |

That fourth row is the one that shapes work: every GPU-memory panel and capacity check in ch06/ch14 reads `/proc/meminfo`, never `cudaMemGetInfo` alone [med]. Concrete facts worth carrying forward, all [med]:

- **Hardware** ([hardware.html](https://docs.nvidia.com/dgx/dgx-spark/hardware.html)): 20-core Arm (10× Cortex-X925 + 10× Cortex-A725); Blackwell GPU, 5th-gen Tensor Cores, 6,144 CUDA cores; 128 GB LPDDR5x unified, 256-bit, 4266 MHz, **273 GB/s**; 1 TB or 4 TB self-encrypting NVMe; ConnectX-7 with 1× RJ-45 10 GbE + 2× QSFP, Wi-Fi 7, Bluetooth 5.4; 4× USB-C, 1× HDMI 2.1a; 240 W external PSU, GB10 SoC TDP 140 W; 150 × 150 × 50.5 mm, 1.2 kg. Our `lscpu`/`free -g` confirm the 20-core split and 121 GB usable (`CLAUDE-CHECKIN.md`).
- **First boot** ([first-boot.html](https://docs.nvidia.com/dgx/dgx-spark/first-boot.html)): language/timezone → keyboard → terms → username/password → info-sharing → Wi-Fi (auto-skipped if Ethernet already has internet) → device joins network and tears down its own AP → automatic full-image install, ~10 minutes with possible reboots → final reboot.
- **Container runtime** ([nvidia-container-runtime-for-docker.html](https://docs.nvidia.com/dgx/dgx-spark/nvidia-container-runtime-for-docker.html)): the toolkit ships preinstalled and preconfigured. Rootless setup is `sudo usermod -aG docker $USER` then `newgrp docker`; verify with `nvidia-ctk --version` (ours reports 1.20.0); the GPU test is a `docker run -it --gpus=all nvcr.io/nvidia/cuda:13.0.1-devel-ubuntu24.04 nvidia-smi`.
- **DGX Dashboard** ([dgx-dashboard.html](https://docs.nvidia.com/dgx/dgx-spark/dgx-dashboard.html)): remote at `http://localhost:11000` through NVIDIA Sync or `ssh -L 11000:localhost:11000 <user>@spark-abcd.local`; per-user JupyterLab ports listed under `/opt/nvidia/dgx-dashboard-service/`.
- **NVIDIA Sync** ([nvidia-sync.html](https://docs.nvidia.com/dgx/dgx-spark/nvidia-sync.html)): Windows/macOS/Ubuntu client automating SSH, port-forwarding and tunnels; three modes — direct LAN, Tailscale for off-network, app launching — plus a Cluster Assistant.
- **NGC** ([ngc.html](https://docs.nvidia.com/dgx/dgx-spark/ngc.html)): `docker login nvcr.io` with username `$oauthtoken`; its example pull `nvcr.io/nvidia/pytorch:24.08-py3` is *older* than the CUDA 13.0.1 tag on the container-runtime page, so re-check current tags before ch04 freezes any.
- **ConnectX-7** ([spark-clustering.html](https://docs.nvidia.com/dgx/dgx-spark/spark-clustering.html)): each QSFP port runs up to 200 Gb/s; approved cables Amphenol NJAAKK-N911 or Luxshare LMTQF022-SD-R; the NIC hangs off the SoC over two independent PCIe Gen5 ×4 links, and each QSFP port produces 4 Linux interfaces (2 Ethernet + 2 RoCE) — 8 with both cabled, named `enp1s0f0np0`/`rocep1s0f0` and `enp1s0f1np1`/`rocep1s0f1`.
- **Updates** ([os-and-component-update.html](https://docs.nvidia.com/dgx/dgx-spark/os-and-component-update.html)): the Dashboard is "the primary and recommended way"; manual fallback is `sudo apt update`, `sudo apt dist-upgrade`, `sudo fwupdmgr refresh`, `sudo fwupdmgr upgrade`, `sudo reboot`.
- **Recovery** ([system-recovery.html](https://docs.nvidia.com/dgx/dgx-spark/system-recovery.html)): 16 GB+ USB, a *wired* keyboard (Bluetooth can't enter UEFI), Esc/Del at power-on, restore UEFI defaults → confirm Secure Boot and "Restore Factory Keys" → Boot Override into the recovery USB. The reflash is explicitly irreversible.
- **Support** ([support.html](https://docs.nvidia.com/dgx/dgx-spark/support.html)): AI Enterprise support for DGX Spark needs the specific "NVIDIA AI Enterprise—DGX Spark" entitlement; field diagnostics are `sudo init 3` then `partnerdiag --field` under `/opt/nvidia/dgx-spark-fieldiag`, about 30 minutes, and ConnectX-7 testing additionally needs DOCA OFED.

Nothing in this bucket failed to fetch. What was never fetched: `software.html`, `uefi-settings.html`, `system-overview.html`, the enterprise fleet/custom-install pages, `pxe.html`, `nvaie-quickstart.html`, every porting-guide child page (CUDA on UMA, memory reporting, profiling), and [build.nvidia.com/spark](https://build.nvidia.com/spark) — which `common-use-cases.html` itself names as "the single source of truth for your Spark device."

## 3. Kubernetes on GB10

### k3s is the proven path; k3d is not

Nobody has run k3d on real DGX Spark hardware. Every first-hand report of Kubernetes on a GB10 box uses plain k3s or Talos. That is **[3-0]** in `verify.json`: all three lenses checked "k3d with GPU is not documented on any DGX Spark" and none refuted it — k3d's own CUDA guide is still the only k3d+GPU documentation that exists, and it has never been run against GB10.

Two exact sequences show up, and they disagree on container runtime. [Collabnix's Docker-runtime walkthrough](https://collabnix.com/setting-up-a-k3s-kubernetes-cluster-on-nvidia-dgx-spark-with-full-gpu-support/):

```bash
# expected — verify on the box (never run on spark-dd06; k3d/kubectl/helm are not installed yet)
sudo nvidia-ctk runtime configure --runtime=docker --set-as-default
sudo systemctl restart docker
curl -sfL https://get.k3s.io | sh -s - --docker --write-kubeconfig-mode 644 --disable traefik
helm install gpu-operator nvidia/gpu-operator --namespace gpu-operator --create-namespace \
  --set driver.enabled=false --set toolkit.enabled=false --wait
kubectl get nodes -o json | jq '.items[].status.capacity'   # look for "nvidia.com/gpu": "1"
```

`driver.enabled=false` / `toolkit.enabled=false` are there because DGX OS ships both preinstalled — confirmed on our box (`nvidia-ctk` 1.20.0, driver 580.173.02, `CLAUDE-CHECKIN.md`). Feeds ch08, ch09.

[Collabnix's containerd-based GB10-specific article](https://collabnix.com/nvidia-dgx-spark-kubernetes-run-gpu-workloads-on-the-gb10-grace-blackwell-superchip/) — the single most load-bearing source in this section — configures containerd directly instead:

```bash
# expected — verify on the box
sudo nvidia-ctk runtime configure --runtime=containerd \
  --config=/var/lib/rancher/k3s/agent/etc/containerd/config.toml.tmpl --set-as-default
helm install gpu-operator nvidia/gpu-operator --namespace gpu-operator --create-namespace \
  --set driver.enabled=false --set toolkit.enabled=false --set devicePlugin.version=v0.17.4
```

Its stated baseline: GB10, 128 GB LPDDR5x, driver 580.95.05 (CUDA 12.x), k3s v1.30+, device plugin v0.17.4+ [med]. The driver/CUDA numbers there are *behind* both NVIDIA's release notes and our box — treat the recipe as current, the versions as stale.

The [NVIDIA forum thread from shahizat (Dec 26, 2025)](https://forums.developer.nvidia.com/t/local-kubernetes-cluster-with-k3s-on-nvidia-dgx-spark/355772) is community confirmation this runs on real GB10: set Docker's default runtime to NVIDIA, restart, then `curl -sfL https://get.k3s.io | INSTALL_K3S_EXEC="--docker --write-kubeconfig-mode 644 --disable=traefik" sh -`. It deploys `nvcr.io/nvidia/vllm:25.12-py3` serving Qwen3-4B with a 50 GB PVC, an HF-token Secret, `nvidia.com/gpu: 1`, 8 CPU / 16 GB limits and a port-8000 Service; the pod went Running after **38 minutes** [med]. A commenter floated Talos Linux 1.12 with a 6.18 kernel; another got the NVIDIA network-operator working for multi-node GPU+RDMA. Feeds ch08, ch09. [k3s's own docs](https://docs.k3s.io/advanced#nvidia-container-runtime-support) describe a simpler third path: install the `nvidia-container-runtime` packages, then install or restart k3s — it auto-detects and wires the runtime into containerd with no template edit. Verify with `grep nvidia /var/lib/rancher/k3s/agent/etc/containerd/config.toml`; if NVIDIA isn't the default, pods need `runtimeClassName: nvidia` [med]. Before any of that, the failure to expect on a fresh box: [Invalid Runtime Name: nvidia](https://forums.developer.nvidia.com/t/invalid-runtime-name-nvidia/350646) — `docker: Error response from daemon: unknown or invalid runtime name: nvidia` on DGX Spark/GB10 ARM64 (Nov 8, 2025) even with nvidia-container-toolkit 1.18.0-1 installed. An NVIDIA moderator (Dec 10, 2025) confirmed the toolkit ships preinstalled but *not fully configured for user access*; the fix is `nvidia-ctk runtime configure` then a Docker restart. A Dec 11 follow-up notes `--gpus=all` alone may work without naming the runtime [med]. Feeds ch02, ch08. What "proven" does not cover: nested k3s. [NemoClaw issue #878](https://github.com/NVIDIA/NemoClaw/issues/878) reports an *embedded* k3s inside another product's gateway container failing to initialize on DGX Spark GB10 / Ubuntu 24.04 / cgroup v2 — kubelet `Failed to kill all the processes attached to cgroup / os: process not initialized`, system pods stuck CrashLoopBackOff, persisting even with Docker's host cgroup namespace mode. Standalone GPU workloads (a ~70 GB Nemotron vLLM) ran fine on the same host, which isolates it to k3s-inside-a-container, not GPU access [med]. Whether a bare-host k3s or k3d install hits the same wall is a smoke test, not an assumed blocker. Feeds ch08.

### Device-plugin floor and the UMA / NVML issue

**[3-0]** across all three lenses: GB10's unified memory makes the classic NVIDIA device plugin fail on `nvmlDeviceGetMemoryInfo` ("Not Supported"), and the fix is device-plugin **v0.17.4 or newer**.

The mechanism, per the [Collabnix GB10 article](https://collabnix.com/nvidia-dgx-spark-kubernetes-run-gpu-workloads-on-the-gb10-grace-blackwell-superchip/): there is no discrete framebuffer for NVML to query, so the plugin crashes on that call. Its troubleshooting table maps `error getting device memory: Not Supported` → old plugin; node shows 0 GPU capacity → plugin crashed, check `kubectl logs -n gpu-operator -l app=nvidia-device-plugin-daemonset`; pods stuck Pending → apply the time-slicing config; CUDA OOM → lower `--gpu-memory-utilization` to 0.8. [NVIDIA's k8s-device-plugin v0.17.4 release notes](https://github.com/NVIDIA/k8s-device-plugin/releases/tag/v0.17.4) carry the exact changelog line — "Ignore errors getting device memory using NVML" (PR #1374) — alongside golang 1.23.12, go-nvlib 0.7.4 and CUDA 13.0.0 bumps. The notes never name GB10 or DGX Spark; that tie comes from community bug reports. One inconsistency the staleness lens flagged and I am carrying forward honestly: an automated fetch attributed the same changelog line to **v0.18.1**, so confirm the version against [the releases list](https://github.com/NVIDIA/k8s-device-plugin/releases) before pinning it in a chart value.

The tie is real. [kubernetes-sigs/dra-driver-nvidia-gpu #1073](https://github.com/kubernetes-sigs/dra-driver-nvidia-gpu/issues/1073) documents an actual DGX Spark GB10 node — Talos Linux v1.13.0-rc.0 (ARM64), Kubernetes v1.34.3, DRA driver v25.12.0, GPU Operator v26.3.1, driver 595.58.03 — hitting `error getting memory info for device 0: Not Supported`, because that driver lacked the graceful fallback the standard plugin got in v0.17.4. Fixed via PR #1121 targeting DRA driver v0.4.0. This is the strongest evidence GB10 runs under real Kubernetes today, via Talos, with GPU scheduling working [med]. The community-empirical lens adds two more independent reports of the identical symptom: [NVIDIA/k8s-device-plugin #1482](https://github.com/NVIDIA/k8s-device-plugin/issues/1482) and [Project-HAMi/HAMi #1511](https://github.com/Project-HAMi/HAMi/issues/1511).

MIG is unavailable on GB10, so time-slicing — temporal sharing, no memory isolation — is the only GPU-sharing mechanism. The Collabnix ConfigMap exposes 1 physical GPU as 4 slices via `sharing.timeSlicing.resources` with `replicas: 4`, then:

```bash
# expected — verify on the box
kubectl patch clusterpolicy/cluster-policy -n gpu-operator --type merge \
  -p '{"spec":{"devicePlugin":{"config":{"name":"time-slicing-config","default":"any"}}}}'
```

The primary-docs lens checked this against NVIDIA's MIG User Guide and found GB10/DGX Spark absent from the supported-GPU table entirely (only A100/A30/H100/H200/B200/RTX PRO 6000/5000 Blackwell are listed) — consistent with non-support, not an explicit vendor statement. So the MIG-unavailable claim is **[med]**, not [3-0]. It sets a real ceiling: any multi-tenant GPU story in ch08/ch09 designs around time-slicing's lack of memory isolation.

### The k3d CUDA node image

[k3d's own docs](https://k3d.io/stable/usage/advanced/cuda/) say CUDA workloads need the NVIDIA Container Runtime with containerd configured for it, and that "the NVIDIA container runtime is not supported on Alpine yet" — the stock k3s node image is Alpine-based. The documented fix is a custom node image: swap the base to `nvcr.io/nvidia/cuda:$CUDA_TAG`, install the toolkit, run `nvidia-ctk runtime configure --runtime=containerd`, copy in the k3s binaries, bundle the device-plugin daemonset under `/var/lib/rancher/k3s/server/manifests/`. Every GPU pod must set `runtimeClassName: nvidia`. Launch is `k3d cluster create gputest --image=$IMAGE --gpus=1`. **The page never mentions arm64 anywhere** — architecture-silent, not arm64-confirmed. Feeds ch08, ch02.

[k3d-io/k3d issue #1108](https://github.com/k3d-io/k3d/issues/1108) (closed via PR #1430, the source of that docs page) adds detail: verify the host with `docker run --rm --gpus all nvidia/cuda:11.8.0-base-ubuntu22.04 nvidia-smi`; the node image should copy only `/bin` plus `/etc`, point `CRI_CONFIG_FILE` at the crictl config under `/var/lib/rancher/k3s/agent/etc/`, and ship a containerd template with `default_runtime_name = "nvidia"`. No arm64 discussion anywhere in the thread — it is literally the only k3d issue matching "arm64"+"cuda", and it does not cover arm64. **[3-0]** as *unproven on arm64*: primary-docs (k3d's text never mentions arm64), community-empirical (no first-hand k3d-on-GB10 thread exists), and staleness (the 88plug/k3d-gpu project, active into early 2026, still documents the same Alpine swap with no arm64 fix) all agree. Unproven combination, not a documented blocker.

### GPU Operator on arm64

[GPU Operator 26.7 release notes](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/26.7/release-notes.html) treat Grace-family hardware as first-class — GH200 as a technology preview needing Ubuntu 22.04 and open kernel modules, GB200 with Fabric Manager partitioning notes, "Coherent Driver Memory Management (CDMM) is enabled by default" on Grace systems, GDRCopy supported on "ARM64 architectures," IGX Orin listed as ARM-based. **GB10 and DGX Spark are named nowhere** [med]. [The releases list](https://github.com/NVIDIA/gpu-operator/releases) shows 26.7.0 latest, then the 26.3.x, 25.10.x and 25.3.x lines — and v26.3.1 is what the real GB10 node in the DRA bug report runs, so the docs lag actual use by at least one minor line [med].

An unresolved version-namespace mismatch to settle before ch09 pins a recipe: Collabnix passes `--set devicePlugin.version=v0.17.4` (a sub-component version) while the `dgx-spark-vllm-k8s` prerequisites table cites GPU Operator v26.3.2 (a whole-chart version). Two different things.

### What nobody has proven yet

Multi-node GB10 clusters exist in the wild, field-hacked rather than vendor-blessed. [rajsinghtechbot/dgx-spark-vllm-k8s](https://github.com/rajsinghtechbot/dgx-spark-vllm-k8s) runs DeepSeek-V4-Flash tensor-parallel across two GB10 nodes over NCCL/RoCEv2 on a direct 200GbE link. Its UMA finding is concrete: a container's `resources.limits.memory` caps GPU allocation too — of the ~119.67 GiB `nvidia-smi` reports, ~24–29 GiB is driver/hardware reserved, leaving **~90–95 GiB effective**. Empirically an 85 GiB limit OOM-kills during model load, **93 GiB is stable**, 95 GiB fails to schedule [med]. Prerequisites: k3s v1.32+ or Talos, Cilium ≥1.18 native routing, Multus, Spiderpool 1.2.x, GPU Operator v26.3.2. It also documents a crashing vLLM leaking ~31 GiB of CUDA context per cycle — after 3–4 crash-loops there is not enough free memory to restart, fixed by `nvidia-smi --gpu-reset -i 0` on startup — and that headless worker pods must run with **no liveness/readiness probes**, since a probe failure kills the pod mid-NCCL-collective and hangs the head. Measured decode: **~17–42 tok/s** at 0.75 GPU memory utilization, 1M context, 2 concurrent sequences, fp8 KV cache; TTFT ~6.3 s at 32K input [med], single-sourced. Feeds ch06, ch08, ch09, ch22.

[vroomfondel/dgxarley](https://github.com/vroomfondel/dgxarley) — self-labeled "development/experimental" — runs a heterogeneous cluster (1 x86_64 control plane + 4 DGX Spark ARM64 compute nodes over a QSFP mesh) for SGLang pipeline-parallel serving. Two K3s gotchas worth flagging: K3s stores CNI configs under `/var/lib/rancher/k3s/agent/etc/cni/net.d` rather than `/etc/cni/net.d`, so the Multus container must mount the parent `/var/lib/rancher/k3s/data` for symlinks to resolve; and the device plugin needs a hostPath mount of `/driver-root` for NVML discovery — miss it and it silently falls back to CPU device resolution, while CDI generation needs a writable `/var/run/cdi`. Measured NCCL bus bandwidth: **9.78 GB/s over RoCE vs 2.12 GB/s over TCP (4.6×)**, requiring SR-IOV VFs and privileged RDMA pods [med]. [Collabnix's docker-compose-vs-k8s comparison](https://collabnix.com/docker-compose-vs-kubernetes-on-nvidia-dgx-spark-which-setup-should-you-choose-for-nim-microservices/) frames whether k8s is worth it on one box at all: docker-compose deploys in roughly 10 minutes vs roughly 30 for k3s (the article's own estimate), with NIM container GPU performance identical between the two — the difference is orchestration overhead. Its recommendation: Kubernetes at two or more nodes, docker-compose for single-node prototyping [med]. Worth reading before ch08 commits, because our answer is Kubernetes for a different reason: the Cloudera operators only exist as Kubernetes operators. The gap round also checked whether Cloudera's operator docs say anything about CPU architecture. They do — see §9, where that claim was refuted **[0-3]** and the registry probe settles the real question.

## 8. Cloudera on AWS

### Public Cloud — standing up the environment

Two Terraform paths get a CDP Public Cloud environment running on AWS, and neither is fast enough to spin up per demo without planning around it.

[`cloudera-labs/cdp-tf-quickstarts`](https://raw.githubusercontent.com/cloudera-labs/cdp-tf-quickstarts/main/README.md) wraps Cloudera's own modules. Prerequisites: an AWS account, a Cloudera on Cloud account (60-day free trial), Terraform v0.13+, and a CDP credentials file. The tfvars need `env_prefix` (≤12 chars, lowercase/numbers/hyphens), `aws_region` and `deployment_template` (`public`/`semi-private`/`private`). **Initial deployment takes up to 60 minutes; teardown is ~20** [med]. It stands up the base environment only — Data Hubs and Data Services get added afterwards. Feeds ch18, ch19, ch21.

AWS publishes the alternate path, [`aws-ia/terraform-cloudera-cdp`](https://github.com/aws-ia/terraform-cloudera-cdp), a Partner Solution module provisioning HA infrastructure across 3 AZs: public+private subnets, NAT gateways, Network Load Balancers, ASGs for environment/data lake/data hub, RDS PostgreSQL multi-AZ, two required security groups, cross-account IAM roles, and an S3 bucket with data/metadata/logs/audit locations [med]. Its variables mirror the quickstart plus `ingress_extra_cidrs_and_ports` — **that last one is the lever for letting a home-LAN or Tailscale NiFi/Kafka client CIDR in.**

Cloudera's [VPC and subnets requirements](https://docs.cloudera.com/cdp-public-cloud/cloud/requirements-aws/topics/mc-aws-req-vpc.html) fill in the checklist both paths assume is already done: bring your own VPC and 2+ subnets, best practice is managing that VPC outside Cloudera, DNS enabled, VPC and subnets tagged `shared` for Kubernetes discovery, private subnets tagged `kubernetes.io/role/internal-elb:1`, public subnets `kubernetes.io/role/elb:1` [med] — the easiest step to miss on a first registration. The same doc set describes the control-plane split: the control plane runs in Cloudera's own account/VPC, each customer gets a sub-account/VPC, and cross-account IAM plus SSL route management traffic between them. The [IAM requirements page](https://docs.cloudera.com/cdp-public-cloud/cloud/aws-refarch/topics/cloudera-private-link-network-iam-requirement.html) states the same three prerequisite buckets — network, S3, cross-account roles [med].

### GPU instance types and CAII sizing

The [CAII sizing guide](https://docs.cloudera.com/machine-learning/cloud/setup-cloudera-ai-inference/topics/ml-caii-caii-configuration-sizing.html) works a Llama 3.1 70B FP16 example. Recommended instance is **`g5.12xlarge`** (A10G GPUs) as the cost-efficient choice — one instance handles 2 replicas at normal load and autoscales a second at peak or during a rolling update; `g5.48xlarge` is the less cost-efficient alternative. For the 2-replica case at tensor parallelism 2 (2× A10G per replica): **normal traffic 4 A10G GPUs, peak 6, and a rolling update needs 8 additional simultaneously**. Storage follows `S = So + Σ(ri×Si) + Sc`: ~40 GB OS + ~296 GB model artifacts (2×148 GB) + ~20 GB images = 356 GB, rounded to a recommended **512 GB** [med]. Elsewhere the sizing doc records `g5.12xlarge` with Llama 3.1 8B Instruct at two A10G GPUs per replica.

The [CAII/NIM announcement blog](https://www.cloudera.com/blog/business/cloudera-introduces-ai-inference-service-with-nvidia-nim.html) confirms the NIM + Triton foundation and names the three optimization profiles: **Latency** (higher tensor parallelism, minimizes TTFT and inter-token latency), **Throughput** (maximizes tokens per GPU), **Generic** (flexible GPU choice, lower performance). As of the July 2025 Cloudera on Cloud release, GPU-instance-type validators run during NVIDIA model deployment to catch misconfigurations [med]. Those are the same NIM profiles a local NIM exposes, which is the concrete comparison ch05/ch19 needs.

Stated honestly: `verify.json` never checked any of these AWS sizing numbers — its six votes cover DGX Spark hardware/software claims and CAII status, not sizing. Every number in this subsection is **[med]**, single-source, even though the bucket flagged it load-bearing.

### DataFlow inbound connections — the mechanism for pushing in from the edge

Cloudera's [Inbound Connections doc](https://docs.cloudera.com/dataflow/cloud/about-inbound-connections.html) is the concrete way a NiFi flow *outside* the CDP environment — home LAN, Tailscale, a DGX Spark at the edge — pushes into a CDF Public Cloud flow deployment. It gives the deployment a stable public hostname with TLS/mTLS auto-provisioned, on AWS and Azure. The endpoint needs an SSLContextService using the auto-created TLS context; the server cert is signed by a public root CA, and a single Intermediate CA signs client certs for mTLS. **All NiFi Listen-family processors are supported, including custom ones, but the listen processor needs a `StandardRestrictedSSLContextService` named exactly `Inbound SSL Context Service`**, auto-populated at cluster deployment [med]. No manual security-group work on the Cloudera side. The [companion announcement](https://community.cloudera.com/t5/What-s-New-Cloudera/Cloudera-DataFlow-for-the-Public-Cloud-introduces-Inbound/ba-p/343616) names a ready-made ListenHTTP "filter to Kafka" ReadyFlow that schema-validates incoming events against Schema Registry before writing to a topic [med] — an off-the-shelf pattern for a local NiFi to POST HTTPS in, get validated, and land in Kafka without exposing a broker. Feeds ch10, ch18, ch19, ch20.

### Data Hub — direct Kafka from outside the VPC

When CDF is not in the picture, [Connecting Kafka clients outside VPC](https://docs.cloudera.com/cdf-datahub/7.3.1/connecting-kafka/topics/kafka-dh-connect-clients-outside-vpc.html) gives the requirements: the VPC needs a public IP, inbound and outbound enabled on the broker port — default **9093**. Client auth is `security.protocol=SASL_SSL`, `sasl.mechanism=PLAIN`, with the FreeIPA cert imported into the client truststore via `keytool` plus a workload username/password. Broker hostnames must be pulled per-cluster from Cloudera Manager and hardcoded — there is no documented DNS naming pattern [med]. This is the fallback path to the inbound-connection route above.

### Iceberg

The [Cloudera Iceberg REST Catalog overview](https://docs.cloudera.com/runtime/7.3.1/overview/topics/cr-ds-cloudera-iceberg-rest-catalog.html) describes Cloudera's server-side implementation of the Iceberg REST Catalog Open API, extended with Ranger for authorization and Knox as gateway. It exposes table metadata to REST-enabled engines — Apache Spark, Trino, Snowflake, AWS Athena, AWS EMR, Databricks — and Athena has been shown querying Cloudera-maintained data through it [med]. A local Iceberg/NiFi pipeline on the DGX Spark could in principle target it the same way, but **the exact external auth flow is unverified** and the source itself flags that. ### Base / Community Edition on EC2

[`cloudera-labs/cloudera-ce-aws`](https://cloudera-labs.github.io/cloudera-ce-aws/) is the Terraform+Ansible bundle for a full CDP Base "Community Edition" cluster on EC2 — on-prem-style deployment on cloud infrastructure, distinct from the SaaS environment above, and the repo is cloned on this box at `/home/tunas/cloudera-ce-aws`. It deploys a ring-fenced ~11-node cluster (project docs say 10; our own run counted 11 — `blog/cloudera-ce-cm-evaluation.md`) reachable only via SSH and reverse HTTPS proxies, with topology options for an Ozone-enabled base, Kafka, Flink, NiFi, CSA and ECS. Every dependency is baked into an Ansible execution-environment image, so the local machine needs a clone, a venv, `ansible-core` + `ansible-navigator`, a container runtime, AWS SSO and a Cloudera license. **A full deployment takes approximately 40–50 minutes**; the cluster is self-contained for DNS, Kerberos, database and Auto-TLS [med]. Two operational gotchas: the license must be the plain text file, not the zip, set via `CDP_LICENSE_FILE`; and AWS SSO credentials expire after 8 hours, so a playbook failing on credentials means refresh the session, not debug the playbook.

On image architecture I cannot answer: neither the landing page nor the getting-started page states amd64 vs arm64 anywhere, and settling it needs the repo's Ansible role defaults or AMI-selection variables. On inbound paths, this architecture is the opposite of Data Hub's: the whole cluster sits behind SSH and reverse HTTPS proxies, so an external NiFi/Kafka client cannot reach it directly at all — it needs a jump host or a reverse-proxy path. **No inbound-connection equivalent exists for CE-on-AWS.** That constraint is what ch18 has to state plainly rather than promise around.

Still open: no pricing or cost-per-hour numbers for either path (the 10-node cluster's instance types were never enumerated, only timings); GPU support on CDP Base/CE is documented only generically (P3+ EC2, YARN GPU scheduling, cgroups isolation, on a 7.1.8 page) and it is unclear whether that applies unmodified inside this topology; and the DNS naming pattern and load-balancer type behind a CDF inbound endpoint were never documented on the pages fetched.

- [CSA Operator 1.1 System Requirements](https://docs-archive.cloudera.com/csa-operator/1.1/release-notes/topics/csa-op-system-requirements.html) — direct fetch confirmed zero mention of x86-64, arm64, aarch64, Graviton or Apple Silicon [med].
- [CSM Operator 1.0 System Requirements](https://docs-archive.cloudera.com/csm-operator/1.0/release-notes/topics/csm-op-system-req.html) — same: OpenShift 4.10+/RKE2 1.23+, CNCF compliance, no architecture text [med].
- [CFM Operator 2.8.0 System Requirements](https://docs-archive.cloudera.com/cfm-operator/2.8.0/release-notes/topics/cfm-op-system-reqs.html) — confirmed no architecture statement [med]. The [2.11.0 index](https://docs.cloudera.com/cfm-operator/2.11.0/index.html) lists the section tree but no distinct 2.11.0 system-requirements sub-page was ever isolated, so its stance is genuinely unknown.

The aggregate — "none of the CFM, CSA or CSM operator docs make **any** statement about CPU architecture" — went through all three lenses and **all three refuted it [0-3]. Do not assert it.** The primary-docs and staleness lenses both point at the same hole: [CFM Operator's installation docs](https://docs-archive.cloudera.com/cfm-operator/2.8.0/installation/topics/cfm-op-install-cfm-op.html) list a `cfmctl-linux-arm64` binary alongside `cfmctl-darwin-arm64` and `cfmctl-windows-arm64` — a direct primary-source architecture statement. The caveat every lens repeats: that is the **CLI client**, not the in-cluster controller or operand images. So the precise wording for the guide is: *the CSA and CSM system-requirements pages are architecture-silent; CFM ships an arm64 CLI; the registry probe above is what actually confirms the container images.* The current-line [CFM Operator 2.11.0 system requirements](https://docs.cloudera.com/cfm-operator/2.11.0/release-notes/topics/cfm-op-system-reqs.html) state Kubernetes 1.23+ / OpenShift 4.10+, persistent storage and cert-manager, with no architecture wording, and [2.11.0's component versions](https://docs.cloudera.com/cfm-operator/2.11.0/release-notes/topics/cfm-op-component-versions.html) pin the operator and `cfmctl` at 2.11.0 bundling NiFi 1.28.0/2.4.0 — worth knowing the operator straddles the 1.x and 2.x lines. [CSA Operator 1.4 system requirements](https://docs.cloudera.com/csa-operator/1.4/release-notes/topics/csa-op-system-requirements.html) require **Kubernetes 1.25+ with a 1.32 ceiling**, and [CSM Operator 1.4](https://docs.cloudera.com/csm-operator/1.4/release-notes/topics/csm-op-system-req.html) states the same window. **That 1.32 ceiling constrains whatever k3d/k3s version ch08 picks** [med].

### Upstream fallbacks, by component

If a future Cloudera image ever turns out amd64-only, here is what upstream ships:

- **CFM/NiFi** — `apache/nifi` Docker Hub images are multi-arch; 2.4.0 and 2.7.2 listings include arm64 layers [med, search-derived]. [NIFI-9177](https://issues.apache.org/jira/browse/NIFI-9177) tracked the original arm64 image request, [NIFI-9554](https://issues.apache.org/jira/browse/NIFI-9554) building on arm64/aarch64. Fallback: vanilla `apache/nifi` 2.x in a plain deployment instead of via CFM Operator.
- **CSM/Kafka** — [Strimzi 0.27.0's release notes](https://github.com/strimzi/strimzi-kafka-operator/releases/tag/0.27.0) state verbatim "Multi-arch container images with support for x86_64 / AMD64 and AArch64 / ARM64 platforms," arm64 flagged experimental *at that 2021 release* [med]. Cloudera's CSM Operator wraps Strimzi directly, which makes this the strongest upstream positive signal in the bucket — though which Strimzi version CSM 1.4/1.5 actually bundles is still unanswered.
- **CSA/Flink** — the [Apache flink-kubernetes-operator GHCR package](https://github.com/apache/flink-kubernetes-operator/pkgs/container/flink-kubernetes-operator) lists `linux/arm64` pulls, but on dev/main commit-SHA tags rather than the numbered 1.13.x release CSA 1.5 embeds, so it is unverified against the release Cloudera ships [med]. It matters because [CSA Operator 1.4's docs](https://docs.cloudera.com/csa-operator/1.4/index.html) say it "is based on the Apache Flink Kubernetes Operator and offers the same set of features." The [`arm64v8/flink` Docker Hub image](https://hub.docker.com/r/arm64v8/flink/) exists as a further fallback [med].
- **EFM / MiNiFi Java** — no container fallback is needed: MiNiFi Java is not shipped as a container, so the fallback *is* the tarball already proven on aarch64.
- **MiNiFi C++** — [Docker Hub's tag list for `apache/nifi-minifi-cpp`](https://hub.docker.com/r/apache/nifi-minifi-cpp/tags) is concrete: `latest` and `1.0.0` both list `linux/amd64` **and** `linux/arm64`, and multi-arch goes back to at least tag `0.15.0`; `0.14.0` and earlier are amd64-only [med]. The [README](https://raw.githubusercontent.com/apache/nifi-minifi-cpp/main/README.md) claims Windows/Linux/macOS support without an explicit architecture sentence. This is a verified arm64 fallback for the agent role.

Cloudera does ship production ARM64 elsewhere, just not (per docs) in the streaming operators: [Cloudera Operational Database](https://docs.cloudera.com/operational-database/cloud/managing-database/topics/cod-aws-graviton-steps.html) supports Graviton2 (I4G) and Graviton4 (I8G) with an explicit ARM64 selector, and [Cloudera Data Engineering](https://community.cloudera.com/t5/What-s-New-Cloudera/Get-started-with-Cloudera-Data-Engineering-on-AWS-Graviton/ba-p/391477) supports Graviton3 for compute nodes [med]. Its [Graviton docs page](https://docs.cloudera.com/data-engineering/cloud/enable-data-engineering/topics/cde-aws-graviton.html) adds an all-or-nothing rule worth knowing: "All Virtual Clusters will run AWS Graviton. Running a subset of Virtual Clusters or jobs on non-Graviton instances is not supported." Both are Public Cloud services, not the operators.

### Local validator and agent-loop patterns

The closest existing analog to "Claude Code talking to this box's GPU and model state" is [dgx-agentskills](https://raw.githubusercontent.com/jeremyeder/dgx-agentskills/main/README.md): a Mac-side plugin plus a containerized MCP server on the box exposing GPU metrics, Docker/Ollama operations and system health over HTTP on **port 3100**. The workflow is `/spark-models pull` → `/spark-models serve` → `/spark-switch local`, which flips Claude Code's base URL to the local endpoint; `/spark-status` runs a health check across system metrics, GPU utilization, model availability and MCP latency before workloads run — a lightweight local validation gate [med]. Check port 3100 does not collide before copying its pattern.

NVIDIA's own [CLI Coding Agent playbook](https://raw.githubusercontent.com/NVIDIA/dgx-spark-playbooks/main/nvidia/cli-coding-agent/README.md) sets up Claude Code, OpenCode or Codex CLI against Ollama at `localhost:11434` on Ubuntu 24.04.3, no Docker images at all. Its validation pattern is the one to copy for ch16: stub a function, write a test, prompt the agent to implement it, run pytest as the end-to-end check [med].

Two playbooks describe sandboxing directly. [OpenClaw](https://raw.githubusercontent.com/NVIDIA/dgx-spark-playbooks/main/nvidia/openclaw/README.md) serves Qwen3.6-35B-A3B-NVFP4 via vLLM at `http://localhost:8000/v1` with no external transmission unless configured. [NemoClaw](https://raw.githubusercontent.com/NVIDIA/dgx-spark-playbooks/main/nvidia/nemoclaw/README.md) wraps the same local model in **four isolation layers — filesystem, network, process, and inference** — framed explicitly against data leakage, malicious execution, unintended actions and prompt injection. That four-layer model is the most ready-made framework in the corpus for "a local model re-checks a command before Claude acts."

Two routing patterns get Claude Code itself onto a local model: a [2026 Medium walkthrough](https://medium.com/@luongnv89/how-to-run-claude-code-codex-with-local-models-via-llamacpp-ollama-lmstudio-and-vllm-2026-7d00ba7e63a4) exporting the endpoint URL, a dummy key and the model name before launching, and [claude-code-router](https://github.com/musistudio/claude-code-router), a local gateway at `http://127.0.0.1:3456` routing across providers — useful if only a cheap local pre-check goes to the box while the main session stays on the API [med].

Two critic/preflight posts come with fetch caveats rather than full reads. ["Agent Safety Gates"](https://medium.com/@ThinkingLoop/agent-safety-gates-12-preflight-checks-before-tools-run-ecf1c41ba252) 403'd — only a snippet, describing a preflight engine that blocks risky tool calls and validates schema/scope/idempotency, with the framing "the most dangerous pattern is tool output → next tool call without validation" [med, unverified]. ["Cross-Model Adversarial Review"](https://codex.danielvaughan.com/2026/03/28/cross-model-adversarial-review/) (snippet only) describes a critic model reviewing a diff in a fresh session given only the spec, test file and diff [med]. Both map onto a locally-served model acting as critic on Claude Code's diffs before they touch live NiFi or Kubernetes.

### Flink Agents and NiFi → local LLM

Flink Agents is real and moving fast, and it is pre-1.0. [0.3.1](https://flink.apache.org/2026/07/25/apache-flink-agents-0.3.1-release-announcement/) shipped 2026-07-25 as the first bug-fix release of the 0.3 line: 5 fixes (Python gateway init, state deserialization during recovery, prompt placeholder substitution, Java tool schema parsing, Anthropic chat-model crashes) plus Flink 2.3 as the default distribution. Supported chat-model providers: OpenAI, Anthropic, **Ollama**, Azure AI, AWS Bedrock, Google Gemini; supported vector stores: Elasticsearch, Milvus, OpenSearch, S3Vectors [med]. [0.3.0](https://flink.apache.org/2026/06/19/apache-flink-agents-0.3.0-release-announcement/) (2026-06-19) added Agent Skills, Mem0-based long-term memory, a durable reconciler, a YAML declarative API and cross-language Python/Java actions — and states outright that "the current APIs and configuration options are experimental and may undergo non-backward compatible changes." The [repo](https://github.com/apache/flink-agents) had 444 stars / 157 forks at the 2026-08-24 fetch, targets Python 3.10–3.12, and publishes no packaged GitHub releases. The [main-branch docs](https://nightlies.apache.org/flink/flink-agents-docs-main/) (v0.4-SNAPSHOT) describe three architectures — Workflow Agent, ReAct Agent, declarative YAML Agent — plus chat models, explicit Tools & MCP support, a three-tier memory model, vector stores and embedding models [med].

**Flink Agents' Ollama support is [3-0]** across all three lenses — it is a built-in provider, not a hand-rolled shim, which turns "Flink Agents on this box calling a local model" from speculative into concrete. Its pre-1.0 status with the explicit non-backward-compatible warning is **[3-0]** too, so ch11 presents it as an evaluation capability pinned at exactly 0.3.1, never a production commitment. The array already has the counterpart data point: `cso-operator-flink-agents:0.3.1` built from source ran stable (JM + 1 TM) on the `cso-prod-1` profile with 199 end-to-end vLLM calls including the tool leg ([#231](https://github.com/cldr-steven-matison/DesktopShare/issues/231), `files/cso-prod-1/VALIDATION.md`).

GPU support in Flink itself is stock. [Flink 1.20's External Resource Framework](https://nightlies.apache.org/flink/flink-docs-release-1.20/docs/deployment/advanced/external_resources/) needs the Kubernetes NVIDIA device plugin v1.10+ and the config keys `external-resources: gpu`, `external-resource.gpu.amount`, `external-resource.gpu.driver-factory.class`, `external-resource.gpu.kubernetes.config-key: nvidia.com/gpu`; operators read GPU info via `getExternalResourceInfos()` [med]. **Flink 1.20 is exactly what CSA Operator 1.5 embeds, so no Flink upgrade is required — only installing the device plugin.** CSO itself has no Flink Agents or GPU story yet. [CSA Operator 1.4.0](https://docs.cloudera.com/csa-operator/1.4/release-notes/topics/csa-op-whats-new.html) runs Flink Kubernetes Operator 1.11.0 + Flink 1.20, turns Python UDFs on by default, adds FIPS mode, removes the v1 SSB REST API — no agents, no GPU. [CSA Operator 1.5.0](https://docs.cloudera.com/csa-operator/1.5/release-notes/topics/csa-op-whats-new.html) — the current target — adds Materialized Views for SSB on Kubernetes, async job handling, embedded Flink Kubernetes Operator 1.13, Postgres 18.1, OpenJDK 17; still Flink 1.20, still no agents/GPU/aarch64 features [med].

On the NiFi side, Cloudera's own documented pattern is the one to lean on: [CFM 4.0.0's release notes](https://docs.cloudera.com/cfm/4.0.0/release-notes/topics/cfm-whats-new.html) confirm CFM 4.0.0 is "based on Apache NiFi 2.0.0 and includes a Python API for developing native NiFi components in Python," and document the ingestion pattern **ParseDocument → ChunkDocument → PutChroma** (the same shape applies to Qdrant) [med] — vendor-documented, not third-party. The [nifi-python-extensions README](https://raw.githubusercontent.com/apache/nifi-python-extensions/main/README.md) confirms scope only and gives no aarch64 notes, leaving OCR/embedding wheel availability (`detectron2_onnx`, `unstructured`) an open question until tested on this box's aarch64. Cloudera's [PromptChatGPT processor doc](https://docs.cloudera.com/dataflow/cloud/nifi-components-nifi2/docs/nifi-docs/components/org.apache.nifi/python-extensions/x/python.PromptChatGPT/index.html) 404'd on direct fetch; a snippet confirms the processor exists and "submits a prompt to ChatGPT" but **no OpenAI-compatible base-URL property could be confirmed from docs** — pointing it at a local vLLM endpoint needs a live check against a running NiFi, not more doc research. The plug point for both NiFi and Flink Agents is the same endpoint. [vLLM's own DGX Spark benchmark](https://vllm.ai/blog/2026-06-01-vllm-dgx-spark) (2026-06-01) serves Nemotron-3-Super-120B-A12B-NVFP4 behind an OpenAI-compatible `/v1` API at `http://localhost:8000/v1`, measuring **22.7–23.7 tok/s decode** across five scenarios and prefill from ~140 tok/s for short prompts to **1,877–1,884 tok/s** for long ones, with `--gpu-memory-utilization 0.85 --max-model-len 131072 --max-num-seqs 4` on `vllm/vllm-openai:cu130-nightly`; it flags a **10–15 minute safetensor load** as distinct from request warmup [med]. A [forum thread on the full local stack](https://forums.developer.nvidia.com/t/running-a-full-llm-stack-on-dgx-spark-gb10-your-application-litellm-llama-swap-vllm-llama-cpp-ollama/367580) describes fronting swappable local models with one OpenAI-compatible router — application → LiteLLM → llama-swap → vLLM/llama.cpp/Ollama — relevant if NiFi and Flink Agents both need one stable endpoint while models change underneath [med, title/snippet only].

The gap is worth stating plainly: the [playbooks README](https://raw.githubusercontent.com/NVIDIA/dgx-spark-playbooks/main/README.md) lists agent-framework playbooks and **zero playbooks for Kafka, NiFi or Flink**, and a direct [forum search for "nifi dgx spark"](https://forums.developer.nvidia.com/search?q=nifi%20dgx%20spark) turned up no threads combining this hardware with NiFi, Flink or Kafka as of 2026-08-24 [med]. **There is no NVIDIA reference implementation for the streaming stack on this box.** ch10, ch11 and the ch21 demos are original integration work, assembled from Cloudera's own CFM pattern doc, NiFi's Python-extension source, and generic local-LLM playbooks. The critic reached the same conclusion from the other direction: zero repos in the whole corpus combine a DGX Spark with any Cloudera component.
