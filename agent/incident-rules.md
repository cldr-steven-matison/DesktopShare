# Incident rules

Each of these came from a real incident. They are the load-bearing "don't do this" list — the shape of every one of them is *this specific thing has already burned real production once, don't repeat it*.

These rules are universal across every device in `../CLAUDE-CHECKIN.md`. App-specific rules (thread caps, atomic JSON writes, etc.) live in the app's own CLAUDE.md.

## Sub-agent prompting

A sub-agent does **not** inherit this file or a skill the parent loaded — it reasons from the prompt you hand it plus what is injected before it. Since 2026-08-25 (#247) the `SubagentStart` hook (`.claude/hooks/subagent-context.sh`) injects **`subagent-rules.md`** into every sub-agent before its first prompt.

**Verified live 2026-08-26 (#247), not assumed:** a `haiku` general-purpose sub-agent was asked to report its pre-prompt context with no tools. It came back with `subagent-rules.md`'s five headings **first**, followed by the whole of the project `CLAUDE.md` and the `MEMORY.md` index — ~520 lines — and quoted the model-tier rule and "Never end your turn while a process you started is still running" verbatim. So the hook works, and the older blanket claim that a sub-agent sees *none* of `CLAUDE.md` or the memories is **wrong on this device**: it sees both. What it still does not get is `agent/*.md` beyond `subagent-rules.md`, and a parent-loaded skill. Keep handing it the specific rule its task can violate — that part stands, because the file the rule lives in is exactly what it doesn't get — the hard live-system rules, the process discipline (never end a turn with a process still running; command-backed facts only), and the output contract. That file is the single place those rules live for sub-agents; keep it under ~9 KB (the hook truncates at the 10 KB cap) and edit it, not the prompts, when a sub-agent rule changes. `guard.sh` runs on sub-agent tool calls too. What the prompt still has to carry — the general shape:

- **Spell out the success criteria and exact output format** you want back — a sub-agent given a vague goal fills the gaps with its own assumptions, and a wrong one reads as corroboration, not error (the #199 `enc{}` case: a `Plan` sub-agent independently reached the same wrong conclusion the parent had).
- **Hand it any domain rule its task can actually violate** — the specific one, in the prompt, not a pointer to a file it can't read.
- **Name the `model` on every `Agent` call, and never run a wait on the session model** — an unset model inherits the session model (the top tier), so a file listing bills at the highest price. The tiers (`haiku`/`sonnet`/`opus`-`fable`), the `run_in_background` alternative, and the base-model/effort cost policy are the canonical rule in `workflow.md` §"Model, effort & context hygiene"; `guard.sh` rules 9 and 10 enforce both. (2026-08-25, #244 → #247: Steven said "optimize lower model execution and not run task waits on highest cost model" three separate times in one day; each later session still launched model-less agents and ran `until … sleep` polling loops on the top model.)
- **Prefer giving it retrieval work** — read the big file, return only the conclusion — so large dumps stay out of the main context. Ask for the conclusion or data, not narration.

## NiFi flow edits

- **Never GET-then-PUT a NiFi processor entity that has sensitive properties.** NiFi returns `"********"` on GET for a sensitive property; a PUT of the returned entity writes that literal string back and destroys the real value. The fix is one of:
  - Bind the sensitive property to a **Parameter Context** (`#{param-name}`) and manage the value there — write-only via API, immune to the mask.
  - Or use the narrow-scope endpoint that only sends the field you're changing (e.g. `PUT /processors/{id}/run-status` — revision + state only, no property payload).
  - Or PUT the full entity with the real sensitive values re-supplied inline in the same call.
  - Check every processor's property descriptors for `sensitive: true` before any full-entity PUT, regardless of what the edit is for — `validationStatus: VALID` never proves a sensitive value is real.
- **Live flow.json is truth. Docs lag.** Before editing a running PG, dump the live flow and read what's actually there. Don't rely on a memory or doc that says "the processor is configured X" — read the flow.
- **But `flow.json` is truth for structure and state only — never for whether a sensitive property is a Parameter Context reference.** NiFi persists the *resolved* value of a `#{param}` reference as `enc{...}`, indistinguishable from a real inline literal; `GET /processors/{id}` masks both as `********`. The authoritative check is `GET /parameter-contexts/{id}` → `component.parameters[].parameter.referencingComponents[]`. (2026-08-21, issue #199: read `enc{...}` on `TwitchChatListener` as "the Parameter Context migration regressed to literals", told Steven his credentials were unmigrated, and re-ran a migration done 2026-07-25 that had held the whole time — about a third of that session. No damage, but the claim was wrong and it was propagated into a subagent's design before it was tested.) Also in the skill: `SKILL.md` rule 1's carve-out and `references/flow-api.md` §5.
- **Any sub-agent given NiFi/EFM flow or API work must be handed the relevant skill rules in its prompt** — it does **not** inherit a parent-loaded skill or this file (see §"Sub-agent prompting" for exactly what a sub-agent does and doesn't get). At minimum, spell out the rule the task can actually violate: GET-then-PUT on sensitive properties, `enc{}` ≠ literal, new logic goes in its own new PG, `Retry` is not `Failure`. (2026-08-21, #199: a `Plan` sub-agent working without the skill independently reached the same wrong `enc{}` conclusion the parent had, and built a whole prerequisite-migration runbook on it — which read as corroboration rather than as the same blind spot twice.)
- **Load the `nifi-and-ai` skill before the first live write to a NiFi/EFM system in a session — a clean prior task on a *different* system doesn't cover it.** (2026-08-11, issue #136/#142: after cleanly rebuilding StarlinkAI's EFM flow via the EFM Flow Designer API, went straight into editing central NiFi's live `TwitchChatBot` PG on the same momentum, without loading the skill for that system. Broke skill rule 8, "build new logic in its own new, finite Process Group — never inline inside a live one": wired new processors directly into the running shared PG instead of an isolated one. Steven caught it mid-edit.) EFM device-class flows and central NiFi's shared PGs are different risk classes — check the skill per system, every session, not once per session. Mechanically enforced since 2026-08-21 (#192/#199): `guard.sh` rule 8 **denies** a curl-style live write to `/nifi-api/` or `/efm/api/` while the skill hasn't been loaded this session, with the fix in the denial text — a backstop for the common path, not a substitute for loading the skill.

## EFM agent deployment

- **Never hand-build an EFM agent-deployer command, and never reuse an `agentIdentifier` across a new enrollment.** Same shape as the GET-then-PUT rule above: a documented-safe API path exists, and skipping it for a hand-rolled equivalent causes real breakage. The only sanctioned source for a deployer command is EFM's **Deploy Agent CLI** screen or its backing API `POST /efm/api/agent-deployer/generateCommand` (omit `agentIdentifier` — the server mints a fresh, collision-free one). Do not hand-construct the `curl`/`Invoke-WebRequest`, and do not copy a previous deployment's command and edit its fields.
  - Reusing an identifier is correct in exactly one case: restoring the *exact same* bare pod that was never de-registered (its saved manifest carries the original `agentIdentifier` so it re-registers as the same EFM agent). A *new* pod, a *class migration*, or any fresh enrollment is not that case — it needs its own identifier.
  - Any sub-agent handed a "recreate/re-enroll this MiNiFi pod" or "move this agent to a new class" task must be told this explicitly in its prompt (it doesn't inherit this file — see §"Sub-agent prompting") — left to its own judgment it will copy-edit the previous command. The `nifi-and-ai` skill (`SKILL.md` "Deployment shapes" + `references/minifi-efm.md` §4) carries the same rule for skill-invoking agents.
  - (2026-08-06, issue #127: consolidating `KubernetesPodJava` into one `KubernetesPod` class, the Java agent was re-enrolled with a hand-built `curl` that reused the retired agent's `agentIdentifier`; the C2 `UPDATE` flow-push failed twice with `state: FAILED` and the Agents update-status column showed errors. Fixed by re-enrolling via `generateCommand` with its server-generated identifier.)

## Fixes and claims

- **Do exactly what's asked. No more, no less.** Don't bundle an unrequested "obvious improvement" into a fix. A rename ≠ a rewire ≠ a retype. If the improvement is obviously worth doing, mention it and ask — don't ship it silently.
- **Don't call something "fixed" until the fix's mechanism actually explains the reported symptom.** Adding logging isn't a fix; it's visibility. If the symptom is "silent drops" and your change adds log lines, say "added logging so we can see the next occurrence," not "fixed the drops."
- **State plainly what happened.** When something broke, one sentence: what happened, what's being done. No justification padding, no explanatory framing before the answer.
- **A fix is "confirmed" only when driven through the actual user trigger, or the exact endpoint that trigger hits.** Before claiming, name the real dispatch path from the doc the ladder points at or from the live flow, then drive that path. A side path that merely resembles it proves nothing. (2026-09-07, #307: screen2 stopped showing a stream; the fix was "confirmed" by POSTing to a local `:5902` listener, but the real `!load … screen2` dispatches through the native MiNiFi Java agent on `:8082`, which was running in Windows Session 0 and launching an invisible mpv. `completed/claude-screen.md` already held the real path.) Known-patterns row `screen-loader` injects those docs at the call site.
- **Check in the moment the root cause is known, before the first fix; and again before anything expensive or irreversible, with the cost stated.** One short message: what is broken, why, what changes. A firmware rebuild, a reflash of a working board, a platform build measured in minutes is Steven's call, not a build step. (2026-08-22, #220: twelve files, a new linter and regenerated screens in one silent 25-minute run. 2026-08-27, #262/#263: an app-level complaint became two full ESP-IDF rebuilds and reflashes, ~20 minutes on the top model, when the documented path was a 20-second littlefs flash. Guard 15 asks before a full AMOLED platform build.) When he pushes back on the silence, the reply is two lines, not a recap.
- **A flag that exists so the user picks what is active per run is never inferred from "what I just worked on", and never given a "sensible default".** Read what the target has active now and pass exactly that (the `cso-operator-app` `MODULES` case: `kubectl exec <pod> -- env | grep MODULES`, then deploy with that value; three occurrences, 2026-07-17/18/26, the first an overnight outage). The same holds for any per-run selection flag in any repo.
- **When the fastest path to ground truth is a cheap live test, run it; don't dispatch research agents to predict it.** A curl, a smoke flow, deploying the proven pattern and looking at the screen beats an hour of Explore agents guessing whether an env var works (2026-07-18: five agents on "can a pod reach WSLg" before one line was tried — "1 hour later still burning tokens"). Reading a bundle, a log or a schema directly is empirical too; the question is whether you hold the fastest path or are guessing at it.
- **After two rounds of "changed X, same symptom", stop varying X.** Read the results as a set: an identical signature across a changing variable rules that layer out. Say so and pivot instead of proposing another X-shaped fix (2026-07-28: four C2 URLs tried in turn for a heartbeat that died the same way each time, plus a real network-profile change, before the pattern was named).
- **On visual feedback, open the artifact before theorizing.** "This looks wrong" about an image, GIF, video or page means extract the frame (`ffmpeg -ss <t> -i <src> -frames:v 1 out.png`) and Read it, then measure rather than eyeball. Two build+deploy cycles went to a wrong mental model of which "overlay" was meant (2026-08-21, #195).
- **Verifying a fix for "Y destroys X" never re-runs Y against real data.** Read back the persisted artifact instead; if a true end-to-end test needs the risky action, that is a wait-for-it-naturally or ask-first situation (2026-07-12: about to overwrite the real watch list and force an unrequested prod restart to prove persistence).
- **A short constraint from Steven is about scope, not architecture; read the sibling and parent issues before treating it as a design mandate.** A board or service shared by several issues usually already has a stated convention one issue over (2026-08-18, #183: "don't replace the OS on the board" became two wrong firmware architectures before the sibling issue's ESP-Brookesia app convention was read — "SPLIT ALL OF THIS"). Match the existing granularity; don't fuse streams and don't over-split.
- **Before building "another X" (a post-to-X flow, a listener, a poster), find the closest existing analog by what it does, not by shape — and build it where Steven said.** "The rest of the flow is in NiFi" is a location, not a preference (2026-07-26: a second tweepy posting path was built in the backend beside the existing `XLivePostProcessor` pattern — "No one ever asked you to even make a backend").
- **A review or "organize this" request applies every fix that ground truth can confirm, in the same pass.** A findings-only report reads identically to staleness a week later (2026-07-24: a confirmed ffmpeg thread fix sat as "findings only, no changes applied" after it had already shipped). Stop to ask only for a judgment call ground truth can't settle.
- **An issue body authored on another device is context, not requirements — especially a concrete contract for a system that isn't running yet.** Deploy the dependency, then derive the design from the running system; when Steven says "the actual X", the *content* of the speculative spec is what is rejected, not just its provenance. Restate the deliverable in one concrete sentence before building after a scope correction (2026-08-21, #205: a wiped leaderboard spec came back as a live-data leaderboard — "AMOLED is the full racing game").
- **Don't substitute a guess for a source you haven't read — and never take a mutating action on the guess.** When a referenced source (a screenshot, a comment, a file) can't be found, search the obvious adjacent locations (the issue you were just on, a `grep` for the exact name) or ask for the link — do not infer plausible content and act on it. Saying "I couldn't find it, working from your description" in prose does not make acting on the guess okay. (2026-08-28, #270/#239: pointed at the wrong issue for a screenshot's feedback, couldn't find it, inferred wrong content, and rewrote a live GitHub issue on the guess — the real feedback was entirely different, so the edit had to be redone. "Guessing and moving on is not going to cut it around here.")

## Credentials

- **Credentials are injected via `kubectl set env`, not in deployment YAML or ConfigMaps.** X, Twitch, Kick, NiFi admin — all live env-vars, deliberately not committed. A `kubectl apply` reporting `deployment.apps/... unchanged` means the env survived — that's what you check after a redeploy, not just rollout status. The failure mechanism when this is broken: a credential field added to `deployment.yaml`/`configmap.yaml` makes the next `kubectl apply` fail with a value-vs-`valueFrom` merge error against the live injected values, and a plaintext credential in a ConfigMap is wrong regardless. A new credential is one `kubectl set env deploy/cso-operator-app KEY=value` call.
- **Never route an authenticated NiFi call through a production-facing pod.** If you need to hit `/nifi-api` with real credentials, do it from `mynifi-0` itself where the k8s secret is already mounted — don't inject the password into an unrelated pod's process list.

## Live service restarts

- **Confirm before restarting any live service — NiFi pod, MiNiFi service, `cso-operator-app` pod — regardless of device.** "This is the correct/sanctioned way to ship the fix" is not the same question as "do I have permission to do it right now." Announcing the action and then doing it is not confirmation. (2026-07-23: redeployed `cso-operator-app` twice without asking; the second restart hit `FetchClips` mid-call and dropped it. Rebuild+redeploy is genuinely the right mechanism for `cso-operator-app` — but that only establishes *how*, not *whether to ask first*.)
- **A single-replica pod restart is not a "sequential build step."** It's the "truly destructive/irreversible" category — an in-flight request gets dropped, not queued or retried. Treat it that way even under general low-friction guidance about not pausing for routine build steps.
- **2026-07-26, happened again, this time with confirmed damage — every redeploy needs a live flow-state check, not just an ask.** Started `FetchClips` earlier in a session, then redeployed `cso-operator-app` multiple times later in that same session without re-checking whether it was still actively running and without a fresh ask each time (one earlier "deploy is okay" got treated as covering later, unrelated redeploys). Confirmed real harm via NiFi provenance: two `FetchClips` `InvokeHTTP` calls died mid-response (`unexpected end of stream`) exactly when those redeploys hit. **Before every single `cso-operator-app` redeploy: (1) check live NiFi state for whether any streamer PG is actively running/mid-fetch — not just the app's own coarse status endpoint — and (2) ask, fresh, every time, regardless of what was already agreed earlier in the session.** (2026-08-12: dropped the old pointer to `feedback_prod_no_manual_patches.md` here — that's a per-device Claude memory file, invisible on other devices; this bullet is the full rule.)

- **Scope of the no-`kubectl exec` / no-manual-patch rule: it is about the unattended Telegram → Claude path.** When Steven is at the keyboard driving the session ("human in the loop now"), `kubectl exec`/`kubectl cp` are fine — prefer reviewable code shipped through rebuild → redeploy when there is a reasonable way, but never refuse `exec` because he is present (clarified 2026-07-03). The live-queue rules in `live-queues.md` still apply to files under `/clips` while fetch/publish is active.

- **An approval through the #192 phone bridge counts as the fresh ask** — Steven answers each bridged question himself (`agent/device-comms.md` "Session comms (Telegram)", classes 1–2). The bridge never auto-allows, and it discards replies stamped before its own ask went out, so a backlog OpenClaw flushes on recovery cannot approve a later redeploy; a session-level Monitor ask must apply the same epoch check (`agent-to-agent.md` "Reply bridge").

- **Never `kubectl delete pod mynifi-0` as a "restart" — it wipes the entire NiFi flow.** The `mynifi` StatefulSet's `data`, `flowfile-repository`, `content-repository`, `provenance-repository`, and `state` volumes are all `emptyDir`, not PVCs (re-verified live 2026-08-12), so a pod delete bootstraps a brand-new empty root process group: every PG, processor config, and controller service is gone. (2026-07-10: deleted the pod to force a Python-extension rescan and lost `StreamersApp` and all four child PGs. Promoted here from device memory 2026-08-12.)

## Port-forwards and tunnels

- **Never start a `kubectl port-forward` or `minikube tunnel`/`minikube service` ad hoc — check for one already running first, and never start a second one on the same target.** The canonical set for WindowsDesktop's `cld-streaming` cluster lives as zellij panes in `~/.config/zellij/layouts/kube-service-ports-efm.kdl`, visible and restartable in the terminal — not as a background process a session or sub-agent quietly owns. Before forwarding anything: `ss -tlnp | grep <port>` or `ps aux | grep -E "port-forward|minikube tunnel|minikube service"`; if a match exists, reuse it (curl/query it) instead of starting a duplicate.
- **A duplicate forward on the same target doesn't fail loudly — it silently orphans, or one of the two goes stale and starts eating requests with zero bytes returned.** 2026-07-29: a `kubectl port-forward svc/efm 10090:10090` on the Tailscale-bound address hung for ~29h (TCP connected, no data) and was misdiagnosed cross-device as tailnet flakiness (issue #11) before being traced to the one hung process. In the same session, a sub-agent doing field-validation work (issue #10) started its own untracked loopback `kubectl port-forward svc/efm` for local testing and left it running past its task; that one also hung and was mistaken for a second EFM outage — the actual fix in that case was unrelated (restarting the `minikube tunnel` pane, which is what serves `127.0.0.1` EFM UI access, not a port-forward at all).
- **Any sub-agent whose task touches a k8s service must be told the zellij-pane convention explicitly in its prompt** (it doesn't inherit the parent conversation — see §"Sub-agent prompting") — left to its own judgment it will just start what it needs. If a sub-agent must start a temporary forward for its own testing, it must tear it down itself before finishing, not leave it running.
- **After a zellij reset on WindowsDesktop, check the first pane before diagnosing anything.** It is `!! minikube tunnel (SUDO PASSWORD)` and blocks on a sudo prompt; unanswered, it takes out the EFM service and every forward downstream, and the failure looks like a dead cluster (`curl` to `:10090` refused, agents gone MISSING), not like a prompt (2026-08-21). The layout opens focused on that pane for this reason; the port-forward panes self-heal in a `while true` loop, the tunnel does not. EFM takes ~187 s to start listening, so forwards die and reconnect on their own during that window.
- **If no pane exists for something genuinely new, that's a `kube-service-ports-efm.kdl` edit to propose, not a background command to run.** Ask before adding a pane; the user starts/restarts the zellij session, not the agent.
- **A new LAN-exposed service port needs two separate pieces of work, not one — the k8s-level port-forward AND a Windows Firewall inbound allow rule on the host.** On WindowsDesktop (WSL2 mirrored networking), the `kube-service-ports-efm.kdl` pane binds the LAN IP and works for same-host testing, but Windows Defender Firewall defaults to `BlockInbound` and silently drops real inbound connections from other LAN devices unless a matching rule exists — the failure looks identical to "the forward isn't up" from the far end. (2026-07-31, issue #52: Mosquitto's pane was live and locally reachable, but the MicroFi/XIAO agent on the same LAN couldn't connect until `netsh advfirewall firewall add rule ... localport=1883` was run, admin-elevated, on the Windows side — something only the user can do, not WSL/Claude.) When adding any new LAN/Tailscale-bound pane: check `Get-NetFirewallRule -Direction Inbound -Enabled True -Action Allow | Get-NetFirewallPortFilter` for the port, and if missing, ask the user to add it via an elevated `netsh advfirewall firewall add rule`.

## Memories are not the instrument

The Claude Code harness tells every session to save memories by default. On this project that instruction is **overridden** (the same way the no-`Co-Authored-By` rule overrides the harness commit trailer): a session never writes a memory on its own — not on a failure, not on a lesson, not on a "useful fact". Steven, 2026-09-07 (#310): "Stop claude default save a memory (it will forget or ignore later anyways)". The evidence behind it: a lesson written to memory is read as a one-line pointer or not at all (the 2026-08-25 flash-gate recurrence, the 2026-08-26 claim-rule inversion), and a wrong memory is obeyed as if verified (2026-09-08: a memory said "write PNGs under `~/Downloads`", the session did, then wrote another memory to record the correction). Between 2026-09-01 and 2026-09-08 the silo on WindowsDesktop grew back from 82 to 85 files while 14 of its rules existed nowhere in the repo.

**What a memory may hold:** device-local facts this box's sessions need and no other device does — local paths, COM ports, local runbooks, hardware quirks. Terse, ≤ 15 lines, `type: reference|project`. Never a `feedback` memory, never a narrative, never a quote, never a rule. Each has `approved: <date> <triggering-event issue URL>` in its frontmatter; `files/memory-lint.sh` fails without it.
